WebKit reference-filter probe

Every swatch starts red. Green means filter: url(#id) reached the pixels.

ctlurlurl+3dchildfn+3d
ctlNo filter. Stays red — it is the reference the others are read against.
urlA plain reference filter. Green everywhere.
url+3dThe one that matters. A reference filter on a composited element. Green means WebKit paints it into that layer's own backing store — so filtering each tile individually works.
childFilter on the parent, composited child inside: the tile-pane case. Expected red. This is the bug.
fn+3dControl. A function filter composites fine, so this must be green. If it is red, the page is broken, not the browser.

Why this exists. The chart depends on filter: url(#id): the water is keyed out of the land tiles that way and the palettes are toned that way. WebKit bars any filter list containing a url() reference from the CoreAnimation compositor (RenderLayerBacking::updateFilters), so a reference filter only runs in the software paint path — and Leaflet gives every tile a translate3d, making each tile its own composited layer whose pixels never pass through an ancestor's software filter.

The answer, measured on an iPhone (2026-08-24): child red, url+3d green. A composited layer that cannot composite its own filter paints it in software into its own backing — so moving the filter onto the tile itself works. That is the @supports (-webkit-touch-callout: none) block at the end of index.html's stylesheet.

When to run it. Open /dev/webkit-filter-probe.html on the device if the chart stops toning on iOS after a Safari release. If url+3d ever turns red, the per-tile fix has stopped working and the next thing to try is filtering the tiles in JS on a canvas.
